# Deep Interview Insights: 온결 공방 — 한국 전통 공예 홍보 웹사이트
> Date: 2026-09-30
> Rounds: 3
> Final Ambiguity Score: 0.17

## Core Problem
로그인 없이 공예품과 체험 클래스를 소개하고, 주문 문의·클래스 신청 흐름을 Mock API(모의 응용 프로그래밍 인터페이스)로 끝까지 재현하는 개발 실습용 프론트엔드 프로토타입이다.

## Key Insights & Decisions
- 사용자는 세부 결정을 대부분 위임했다("알아서", "권장하는대로"). 아래 결정은 인터뷰어 권장안이 확정된 것이다.
- 폼은 모달로 연다. PC는 중앙 다이얼로그, 모바일은 전체 화면 시트이다. 목록 맥락이 유지되고 두 탭이 같은 패턴을 쓴다.
- Mock 오류는 지정 번호(`010-0000-0000`)에서만 발생하며 무작위 실패는 없다. 테스트 결정성을 확보하기 위함이다.
- 실패는 예외가 아니라 `{ ok: false, ... }` 판별 합집합(discriminated union) 결과로 반환한다(제안).
- 잔여석은 표시 전용이며, 신청해도 차감하지 않는다(저장 없음).
- 이미지는 Wikimedia Commons 실제 사진을 쓰고 출처·라이선스를 표기한다. 적합한 사진이 없으면 플레이스홀더로 대체한다.
- `src/` 경로 불일치는 `src/` 구조로 옮겨 해소한다(권장안 채택, 요구사항 명시 경로 존중).
- git은 상위 저장소와 분리된 별도 저장소로 `git init`한다(권장안 채택, 다른 앱과 동일한 방식).

## Defined Requirements

### 구조·탭
- 상단 주요 탭은 정확히 2개이다: 공예품 전시·주문, 공방 클래스.
- 탭은 단일 페이지(`/`) 안에서 전환한다. 라우트를 나누지 않고 WAI-ARIA Tabs 패턴(`role="tablist"`/`tab`/`tabpanel`, `aria-selected`)을 쓴다. 기본 탭은 공예품 전시·주문이다.
  - 2026-09-30 사용자 요구로 변경했다. 인터뷰 당시 제안은 라우트 분리(`/crafts`, `/classes`, `/` → `/crafts` 리다이렉트, `aria-current`)였으며 폐기했다. 확정 내용은 spec.json의 D1이다.

### 데이터 (TypeScript Mock Data)
- 상품 8개: 도자기·나전칠기·보자기·목공예 각 2개. 필드는 id, 이미지, 이름, 공예 종류, 설명, 가격이다.
- 클래스 4개: 필드는 id, 이름, 설명, 가격, 소요시간, 정원, 잔여석이다. 1개는 잔여 0석(마감)이다.
- 가격은 `180,000원` 형식(ko-KR 로캘)으로 표기한다.

### 폼
- 주문 문의: 상품명(자동 입력, 읽기 전용), 이름\*, 연락처\*, 수량\*(1~10), 요청사항(선택, 500자 이내).
- 클래스 신청: 클래스명(자동 입력), 이름\*, 연락처\*, 희망 날짜\*(오늘 이후), 인원\*(1~잔여석), 요청사항(선택).
- 클라이언트 검증: 필수값, 휴대폰 형식 `01X-XXXX-XXXX`, 수량·인원 범위. 오류는 해당 필드 아래에 표시한다.
- 마감 클래스는 신청 버튼을 "마감"으로 표시하고 비활성화한다.
- 모달은 Esc·닫기 버튼으로 닫히고, 포커스 트랩이 있으며, 닫으면 여는 버튼으로 포커스를 되돌린다.

### Mock API (`src/lib/mock-api.ts`)
- 함수 2개: 주문 문의 제출, 클래스 신청 제출.
- 외부 네트워크 요청·저장 없이 약 700ms 지연 후 응답한다. 지연 시간은 테스트에서 조정 가능하게 한다.
- 성공: 가짜 접수번호(예: `ORD-…`, `CLS-…`)와 접수 완료 메시지를 반환한다.
- 실패: 연락처가 `010-0000-0000`(하이픈 없는 `01000000000` 포함)이면 Mock 오류를 반환한다.
- 대기 중 제출 버튼은 "접수 중…"으로 비활성화한다(중복 제출 방지). 실패 시 입력값을 유지하고 "다시 시도"를 제공한다.

### 실습용 안내
- 사이트 상단 상시 배너와 각 폼 상단 한 줄 안내를 둔다. 실제 이름·전화번호를 입력하지 말 것과 실패 테스트용 번호를 안내한다.

### 디자인 (제안)
- 한지 톤 미색 배경, 먹색 텍스트, 포인트 색 1개(쪽빛)를 쓴다.
- 제목은 명조(Noto Serif KR), 본문은 고딕 계열이다. 넉넉한 여백과 가는 구분선을 쓰고, 전통 문양은 쓰지 않는다.
- 반응형 카드 그리드: 모바일 1열, 태블릿 2열, PC 3~4열이다.

### 기술 스택
- Next.js 16.3.7(App Router), React 19.2.8, TypeScript, Tailwind CSS v4.
- 테스트는 Vitest + Testing Library(미설치 상태, 추가 필요)이다. 흐름은 TDD(테스트 주도 개발)를 따른다.

## Success Criteria
1. Vitest 테스트가 전부 통과한다. 대상은 Mock API(성공·실패 번호·지연)와 폼 흐름(검증 오류 → 제출 → 성공/실패 → 재시도)이다.
2. 키보드만으로 탭 전환, 모달 열기·닫기, 제출이 가능하다.
3. 색 대비가 WCAG(웹 콘텐츠 접근성 지침) AA 기준(4.5:1 이상)을 충족한다. 육안이 아닌 계산으로 확인한다.
4. 375px 모바일과 PC 폭에서 가로 스크롤 없이 표시된다.
5. 로컬 `npm run dev` 실행과 `npm run build`가 통과한다.

## Identified Risks & Failure Modes
- Next.js 16은 학습 데이터와 API가 다르다. 구현 전 `node_modules/next/dist/docs/`에서 폰트·이미지·metadata 부분을 확인해야 한다(`AGENTS.md` 지시).
- Tailwind v4는 CSS 기반 테마 정의(`@theme`)를 쓴다. 색 토큰을 이 방식으로 정의해야 한다.
- Commons 사진은 톤이 제각각일 수 있어 선별 시간이 들고, 라이선스 표기 형식을 정해야 한다.
- 모달 포커스 트랩과 포커스 복귀가 누락되기 쉽다.
- `next dev` 실행 중에 같은 `.next`로 `next build`를 돌리면 청크가 깨진다(상위 CLAUDE.md의 함정).
